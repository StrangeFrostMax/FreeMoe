# Analysis of externally supplied FreeMoe documents

**Analysed:** 2026-10-28 on branch `arena/f4ec845c-freemoe`.  
**Source repository:** [riteshnair/FreeMoe](https://github.com/riteshnair/FreeMoe) at commit `6c806c8e4c7cb6ae582dcda3c732f7046103976f` (`Add files via upload`).  
**Files reviewed:** one `.docx`, one `.md` and one `.zip`, exactly as supplied.  
**Outcome:** the three files are planning/specification documents, not implementation artefacts. They describe a substantially larger future system than the current correctness prototype. No runtime code was changed by this analysis.

Extracted text copies, provenance hashes and the ZIP contents are stored under `docs/external/riteshnair-freemoe/`; see `SOURCE.md` there.

---

## 1. Executive verdict

The documents are useful but they are **not a drop-in extension of the current repository**. They introduce a second, much broader project vision:

- The current `StrangeFrostMax/FreeMoe` work is a **disk-resident MoE inference correctness prototype** with synthetic F32 GGUF fixtures, a CPU oracle, a vendored CPU Virtual NPU, paging/residency, checksums, traces and fail-closed tests.
- The `.docx`/`.zip` pair describes a **model-construction and training system** with a native tensor blob store, governor/MCP automation, Windows/CMake tooling and staged implementation gates.
- The `.md` specification describes a **production coding MoE student model** plus a **large-model bounded-residency runtime**, with a detailed mathematical contract, GGUF schema, converter, quantisation pipeline, training/distillation plan and expanded `WAKE_UP` inspection.

**Recommendation:** keep the existing prototype as the stable regression baseline, adopt the `.md` as the candidate v2 model/runtime specification, and use the `.docx`/`.zip` as an implementation-process/gate plan. Do not attempt to implement all gates at once. The lowest-risk next increment is Gate 0/1: generalise GGUF inspection and add a native blob-store round-trip for explicitly supported tensor encodings, without removing `freemoe-tiny-v1`.

## 3. Document-by-document analysis

### 3.1 `FreeMoe_Final_Solution_and_Build_Plan-1.docx`

**Type:** strategic/process plan, version 1.0, dated 28 October 2026.

**Core proposition:** turn FreeMoe into a model-construction system that separates logical architecture from physical tensor storage, reuses existing trained models where possible, and eventually supports sparse MoE with independently paged experts.

Key positions:

- Platform: Windows x64, native C++/CMake, **no mandatory PyTorch dependency**.
- Governor candidate: `minicpm5-1b.i1-q6_k.gguf`.
- First target: a small GGUF model already supported by the existing engine, ideally around 135M parameters.
- First practical gate: inspect the current engine, add read-only GGUF inspection, then implement a native binary tensor-blob store with byte-exact round-trip.
- Explicit boundaries:
  - a GGUF is not a training dataset;
  - IMatrix is not learned knowledge;
  - writing blobs is not training;
  - dense-to-MoE conversion is not a file conversion;
  - disk-first means bounded memory, not zero memory.
- Later phases: governor/MCP tools, teacher-generated examples, logit/hidden-state distillation, compatible weight initialisation, tiny native training proof, explicit MoE architecture, then Vulkan.

The document defines nine gates:

0. repository reconnaissance and clean build;
1. GGUF inspection;
2. blob store and round-trip;
3. inference parity;
4. transactional recovery;
5. tiny native training and resume;
6. governor tools and MCP;
7. small pretrained target and adaptation;
8. experimental MoE and Vulkan.

It also proposes a CLI surface (`inspect-gguf`, `blob-import`, `blob-verify`, `model-validate`, `train`, `resume`, `evaluate`) and explicitly says these are proposed commands, not existing ones. This is important: none of those commands exist in the current CLI.

**Assessment:** this is a sensible staged plan for a training/model-construction product. It is process-heavy and correctly warns against claiming learning from storage or file conversion. However, it assumes a Windows/CMake starting point and a governor model that the current Linux/POSIX synthetic prototype does not support.

### 3.2 `FreeMoe_Model_Math_GGUF_Creation_and_Runtime_Spec.md`

**Type:** detailed technical specification and mathematical contract.

It explicitly separates two deliverables:

1. **FreeMoe-Coder:** a new 1B–2B total-parameter Llama-like coding MoE with roughly 700M active parameters under a stated accounting convention, targeting an 8 GB GPU deployment.
2. **FreeMoe Runtime:** execute larger existing MoE checkpoints, potentially 27B–32B total parameters, with bounded residency and NVMe/RAM/VRAM tiering.

It also says “chunking is not distillation”: the large-model runtime pages original expert tensors; the student is a separate newly trained/distilled model.

#### Proposed `freemoe-coder-v1` dimensions

| Field | Proposed value | Current `freemoe-tiny-v1` fixture |
|---|---:|---:|
| Architecture | `freemoe` / `freemoe-coder-v1` | `freemoe-tiny` / `freemoe-tiny-v1` |
| Layers | 20 | 2 |
| Hidden width | 1,280 | 16 |
| Query heads | 20 | 4 |
| KV heads | 4 (GQA) | 4 (MHA only) |
| Head dim | 64 | 4 |
| Expert intermediate width | 1,920 | 32 |
| Experts per layer | 8 | 8 |
| Top-k | 2 | 2 |
| Context | 4,096 initially | 1,024 |
| Vocabulary | must come from pinned tokenizer | 258, raw byte tokenizer |
| Output head | tied to embeddings | separate `output.weight` |
| Attention | causal GQA | MHA |
| Normalisation | pre-norm RMSNorm, eps 1e-5 | RMSNorm, half-rotation RoPE |
| Position encoding | RoPE theta 10,000, no scaling | RoPE theta 10,000, half rotation |
| FFN | MoE-only SwiGLU every layer | dense or MoE SwiGLU, synthetic |
| Quantisation target | F16, then Q8_0/Q6_K/Q4_K | F32 inference only |

The document uses an example vocabulary of 250,000 only to illustrate parameter arithmetic; it repeatedly warns not to invent the real vocabulary size. With that example, it estimates about 1.58B total parameters and about 694M “active parameter uses” only when the full tied output projection is counted. It insists the accounting convention be stated whenever quoting 700M active parameters.

#### Mathematical contract

The spec defines:

- token embedding;
- pre-norm Transformer layer with RMSNorm, Q/K/V projections, RoPE, causal GQA, output projection and residual;
- MoE-only feed-forward block with linear router, deterministic top-2 (lower expert ID wins ties), softmax over selected logits, SwiGLU experts and weighted sum;
- final RMSNorm and tied output logits;
- causal cross-entropy, optional router load-balancing loss and optional distillation loss with recorded coefficients.

It states that every token must execute exactly two selected experts per layer and that failure to load/execute an expert must be an explicit error.

#### GGUF and converter contract

The spec proposes:

- `general.architecture = "freemoe"` with `freemoe.model_version = 1`;
- a namespaced `freemoe.*` metadata inventory;
- a canonical logical tensor registry independent of source framework names;
- a separate `freemoe-convert` tool with `inspect-source`, `validate-source`, `map`, `dry-run`, `export` and `verify` commands;
- a sidecar conversion manifest with source hashes, tokenizer hash, config hash, per-tensor hashes and per-expert hashes;
- a 13-section `WAKE_UP`/inspection report covering file identity, container, architecture, config, tokenizer, tensors, MoE map, quantisation, memory plan, I/O plan, integrity, compatibility and provenance;
- separate reporting of parser support, architecture support, tensor dtype support, CPU execution support and GPU execution support.

It explicitly says a generic GGUF reader will not execute a custom `freemoe` architecture automatically, and that parsing a quantised tensor is not the same as supporting its execution kernels.

#### Runtime, LMDB, training and tests

The runtime section preserves source-model router semantics and warns against imposing the student router on third-party models. It describes cold/warm/hot tiers, an optional sidecar expert index bound to source SHA-256, VRAM/RAM budget equations, and performance metrics. It also describes a separate optional LMDB knowledge cache that must not be treated as pretrained weights or silently mutate the GGUF.

The training section blocks training until teacher, licence, tokenizer, dataset, hardware, framework, evaluation and seeds are selected. It proposes staged smoke tests, tokenizer contract tests, small-data overfit, teacher data generation, distillation, router validation, coding evaluation, checkpoint export, GGUF conversion, runtime parity, quantisation and release.

The test matrix covers converter/container tests, mathematical parity stage-by-stage, MoE paging tests, quantisation tests and a performance gate on named hardware. It explicitly says Q6_K must not be declared executable until dequantisation and inference kernels pass, and that no performance claim should be based only on the synthetic tiny fixture.

**Assessment:** this is the strongest of the three documents. It is internally consistent, mathematically specific, and aligns with many current project principles (no fake GPU, no selected-expert dropping, no silent CPU fallback, correctness before performance). But it is a specification for a future product, not a description of the current implementation.

### 3.3 `FreeMoe_Final_Implementation_Pack.zip`

**Type:** documentation/agent-brief pack, not a code implementation pack.

Contents:

- `README.md`: start with `docs/FINAL_SOLUTION.md`, then the agent brief and project rules.
- `docs/FINAL_SOLUTION.md`: Markdown version of the DOCX plan.
- `FreeMoe_Final_Solution_and_Build_Plan.md`: duplicate of the same plan.
- `FreeMoe_Final_Solution_and_Build_Plan.docx`: byte-identical copy of the supplied DOCX.
- `docs/IMPLEMENTATION_GATES.md`: condensed gate list.
- `docs/RISKS_AND_BASELINES.md`: warns that chunked storage, tensor formats, CPU training, LoRA, tool calling and GGUF export are not novel individually; compare later with Safetensors, standard checkpoints, in-memory tiny trainers and adapter training.
- `docs/BLOB_FORMAT.md`: versioned header, tensor directory, payload, integrity metadata, manifest generations, staging writes, checksums, recovery, fixed-width fields and explicit byte order.
- `agent/PROJECT_RULES.md`: 15 rules, including inspect before changing, one gate at a time, no mandatory PyTorch, keep source teacher files immutable, no network in blob-format unit tests, report actual test outcomes.
- `agent/CODING_AGENT_BRIEF.md`: asks an agent to inspect the existing C++ engine, build Debug/Release, run tests, implement only read-only GGUF inspection plus minimal blob import/verify, add checksum/bounds/manifest/round-trip tests, then stop before training/MCP/MoE/Vulkan.
- `schemas/model-definition.schema.json`: draft JSON schema for a tiny model definition with F32/I32 tensors and operations `linear`, `relu`, `tanh`, `mse_loss`.
- `examples/tiny-model.json`: a one-input/one-output linear regression example with SGD settings.
- `examples/tiny-dataset.jsonl`: five `x,target` points for `y = 2x + 1`.

**Assessment:** the ZIP is a process pack. It contains no C++ source, no build system, no GGUF writer, no blob-store implementation and no tests. The JSON schema/example are illustrative fixtures for a future tiny trainer; they are not a transformer or MoE model definition. The pack is useful as a checklist and agent prompt, but it is not “final implementation” code.

## 4. Cross-document consistency and conflicts

The DOCX and ZIP are intentionally aligned; the ZIP is essentially the DOCX plan plus short supporting rules and examples. The standalone MD spec is a different, more ambitious document.

| Topic | DOCX / ZIP plan | MD spec | Conflict? |
|---|---|---|---|
| Primary goal | Native blob store, model construction, incremental training, governor/MCP | Production coding MoE student + large-model bounded-residency runtime | Significant scope difference |
| First target | Small supported GGUF, ideally ~135M | 1B–2B student; 27B–32B runtime source | Yes |
| Platform | Windows x64, native C++/CMake | 8 GB GPU deployment profile, later real GPU/Vulkan | Different emphasis |
| Storage | New native blob package with manifests and transactional recovery | GGUF as initial container; sidecar expert index; conversion manifests | Different abstraction |
| Training | Tiny C++ training proof after storage gates | Full teacher/student distillation pipeline with tokenizer and coding eval | MD is much larger |
| Quantisation | Add later, preserve encoding | F16 → Q8_0 → Q6_K → Q4_K sequence | Compatible in spirit |
| MoE | Explicit experimental MoE only at Gate 8 | Defined student MoE from the start and runtime paging for real models | Different sequencing |
| CLI | `inspect-gguf`, `blob-import`, `train`, `resume`, etc. | `freemoe-convert`, `model wake-up`, `memory-plan`, etc. | Two different proposed CLIs |
| Current repo | Inference correctness prototype | Inference correctness prototype | Both acknowledge it as baseline |

Shared principles that align well with the current repository:

- do not claim a GPU backend when falling back to CPU;
- do not skip or substitute a selected expert;
- do not treat GGUF parsing as training data;
- do not claim quantisation execution just because tensor geometry parses;
- do not publish performance claims from synthetic fixtures;
- keep `freemoe-tiny-v1` as a stable regression target;
- correctness and evidence before optimisation.

## 5. Gap analysis against the current implementation

The current repository already implements a narrow version of several runtime ideas: bounded GGUF parsing, `inspect`/`WAKE_UP`, synthetic dense/MoE fixtures, CPU oracle, VNPU backend, expert residency/paging, checksums, typed errors, JSON traces, fuzz/soak tests and a deliberately failing GPU placeholder. The documents ask for much more.

| Capability | Current state | Required by new docs | Gap |
|---|---|---|---|
| GGUF inspection | Works for `freemoe-tiny` F32 fixtures only | General read-only inspection of real GGUF metadata/tensors/dtypes/offsets | Need a parser-level inspector separate from architecture adapter |
| `WAKE_UP` report | Basic inspect JSON with metadata/roles/expert records | 13-section report with support levels, quantisation capability, memory/I/O plan, provenance | Large reporting expansion |
| Architecture adapter | One strict `freemoe-tiny-v1` adapter | `freemoe-coder-v1`, third-party MoE adapters, source-specific router semantics | Multiple adapters and versioned registry needed |
| Tensor types | F32 execution only; Q8_0 geometry probe | F16, Q8_0, Q6_K, Q4_K kernels and independent dequant tests | No quantised inference kernels |
| Attention | MHA with `kv_heads == heads` | GQA with 20 query / 4 KV heads | Adapter and kernel changes required |
| Output head | Separate `output.weight` | Tied embeddings/output projection | New tie semantics and validation |
| Tokenizer | Raw byte tokenizer, no chat template | Pinned real tokenizer with hash and special-token IDs | Tokenizer subsystem needed |
| Expert paging | Synthetic stacked F32 extents, checksums, LRU/clock, traces | Real MoE source models, sidecar expert index, source hash binding | Generalise extent/index format |
| Native blob store | None | Versioned header, directory, payload, checksums, manifest generations, staging/recovery | Entire subsystem missing |
| Converter | Fixture generator and Python GGUF writer/parser | Separate `freemoe-convert` with source validation, mapping, dry-run, export, verify | New toolchain |
| Training | None | Tiny C++ proof, gradient checks, checkpoint/resume, distillation, coding eval | Entire training stack missing |
| Governor/MCP | None | Allow-listed tools, strict schemas, no arbitrary shell/path execution | Later-phase subsystem |
| Physical GPU/Vulkan | Placeholder only, `dedicated_vram_bytes=0` | Real GPU backend after CPU correctness | Gate remains closed |
| LMDB knowledge cache | None | Optional separate mutable store with provenance and recovery | Not started |

The proposed `freemoe-coder-v1` metadata and tensor names would be rejected by the current adapter immediately. For example, the current adapter requires `general.architecture = "freemoe-tiny"`, `freemoe.adapter = "freemoe-tiny-v1"`, `freemoe.rope_mode = "half"`, `freemoe.router_operation = "linear-topk-softmax-v1"`, `freemoe.expert_layout = "stacked-f32"`, `kv_heads == heads`, and specific tensor names such as `blk.L.ffn_gate_exps.weight`. The MD spec proposes `general.architecture = "freemoe"`, `freemoe.model_version = 1`, `rope_mode = "half_rotation"`, `router_operation = "linear_topk_softmax_selected"`, `expert_layout = "stacked"`, `num_key_value_heads = 4` with 20 query heads, and tensor names such as `blk.L.experts_gate.weight` / `blk.L.router.weight`.

## 6. Risks and decision points

1. **Scope explosion.** The docs collectively ask for a converter, blob store, trainer, governor/MCP, quantised kernels, real GPU/Vulkan, LMDB cache and a 1B–2B trained student. Implementing all at once would destroy the current correctness baseline.
2. **Two conflicting product directions.** DOCX/ZIP emphasise generic model construction and training; MD emphasises a specific coding MoE student plus large-model runtime. A product decision is required.
3. **Unresolved inputs.** Teacher checkpoint, tokenizer, vocabulary size, dataset licences, training framework, target GPU and evaluation benchmark are all unspecified. The MD spec correctly refuses to guess them.
4. **Quantisation complexity.** Q6_K/Q4_K support requires block-accurate dequantisation and inference kernels, not just parsing. This is a large correctness surface.
5. **8 GB VRAM claim.** The MD spec’s 1.58B example gives ~3.16 GB F16 raw weights, but KV cache, scratch, allocator reserve and driver use must be measured on real hardware.
6. **Windows vs Linux mismatch.** DOCX/ZIP assume Windows PowerShell/CMake; the current verified build is Linux/POSIX GNU Make with optional CMake.
7. **CLI collision.** The docs propose at least two different future CLI surfaces, neither matching the current `inspect`, `run`, `compare`, `device-info` commands. A consolidation decision is needed.
8. **Provenance.** The DOCX generator metadata is not trustworthy; use the Git commit and SHA-256 hashes recorded in `docs/external/riteshnair-freemoe/SOURCE.md`.
9. **Performance claims.** The docs themselves warn against this; keep performance and physical-GPU gates closed until real hardware evidence exists.

## 7. Recommended adoption path

If the goal is to evolve the current prototype, I recommend this order:

1. **Freeze scope.** Decide whether the next release is:
   - A: inference/runtime only (continue current path);
   - B: model construction/training path (DOCX/ZIP);
   - C: combined product with both student training and large-model runtime (MD).
2. **Keep `freemoe-tiny-v1` unchanged.** All three documents and the current tests benefit from preserving it as a regression fixture.
3. **Add a general GGUF inspector first.** Extend `inspect` so it can report arbitrary GGUF container metadata, tensor directory, dtypes, offsets and support levels without trying to execute the model. This satisfies DOCX/ZIP Gate 1 and part of MD section 7.
4. **Implement the native blob format as an isolated library.** Use fixed-width fields, explicit endianness, checksums, staging writes, manifest generations and recovery tests. Start with F32 byte-exact round-trip. Do not modify the existing engine inference path until parity is proven.
5. **Add a conversion manifest and per-tensor/per-expert hashes.** This is common to both DOCX/ZIP and MD and improves provenance immediately.
6. **Implement F16, then Q8_0, then Q6_K kernels one at a time.** Keep the “parsed” and “executable” support flags separate.
7. **Introduce `freemoe-coder-v1` as a second adapter.** Do not replace `freemoe-tiny-v1`. Add GQA, tied embeddings and the new tensor registry only after the tokenizer/config contract is frozen.
8. **Defer training, governor/MCP, LMDB and Vulkan.** These are later gates and require inputs not present in the repository.
9. **Keep all release gates evidence-based.** No “supported” label without tests; no performance claim without named hardware and repeated measurements.

The smallest useful next pull request would be: general read-only GGUF inspection + a standalone F32 blob writer/reader + round-trip/checksum/corruption tests + documentation. That is consistent with the supplied DOCX/ZIP Gate 1/2 and does not yet require training, MCP or GPU work.

---

## 8. Conclusion

The three documents are coherent as a **roadmap**, but they are not implementation evidence and they do not describe the current runtime. The DOCX/ZIP pair is a careful process plan for a native blob-store/training vertical slice. The standalone MD spec is a much more detailed proposed production architecture and runtime contract. Both are valuable, but they point to a materially larger project than the current synthetic F32 correctness prototype.

**Do not merge them into the codebase as if they were implemented.** Use them to choose the next architecture, then implement one gate at a time while preserving the existing tests and evidence.
